# Измеренная производительность

Измерения выполнены 2026-10-02 на AMD Ryzen 7 8745HS (16 логических CPU), с 16.46 ГБ
оперативной памяти хоста, Docker Desktop Linux/amd64 (7.42 ГиБ памяти виртуальной машины),
Go 1.26.8, GOMAXPROCS=16. Работали другие локальные контейнеры: это общая рабочая
станция разработчика, а не изолированное оборудование для измерений.
Короткие запуски включают вариации планировщика и прогрева соединений.

Для воспроизведения:

```sh
go test -run '^$' -bench=. -benchmem ./...
go run ./cmd/experiment -duration 3s -concurrency 32
docker compose run --rm -e DURATION=10s -e VUS=20 k6
docker compose run --rm -e SCENARIO=rate k6
```

## Контролируемые локальные эксперименты

Клиент, шлюз и бэкенды httptest работают в одном Linux-процессе. Журналирование
использует slog JSON с отбрасыванием вывода; метрики включены, экспортёр трасс отключён.
HTTP работает через локальную петлю без TLS. Каждый сценарий длится 3 с
с 32 работниками. Сценарий поступления создаёт 500 запросов/с; остальные работают
в замкнутом цикле. Оставшиеся в конце запросы отменяются и исключаются из перцентилей
завершённых запросов, но могут учитываться в числе попыток и соединений бэкендов.
Выборка задержек ограничена миллионом значений.

Исходные данные: [experiment-results.jsonl](experiment-results.jsonl).
CPU — фактическая сумма пользовательского и системного времени Linux getrusage
для **общего процесса клиента, шлюза и бэкендов**, а не только шлюза.
JSON сообщает процент загрузки одного ядра; многоядерные запуски могут превышать 100%.
Число соединений получено из `ConnState(StateNew)` бэкенда.

В этом запуске p50 вырос с 0.205 мс при прямом доступе до 0.680 мс через шлюз;
пропускная способность завершённых запросов снизилась. Отключение пула бэкендов
создало примерно одно TCP-соединение на попытку и ещё снизило пропускную способность.
Эти наблюдения относятся к конкретной нагрузке и не определяют поведение в интернете,
с TLS или предельную ёмкость развёртывания.

Циклическая балансировка отправила 1559/1558 запросов на серверы 10 мс/50 мс,
а выбор по минимуму активных запросов — 4240/944. Последний улучшил пропускную
способность завершённых запросов при этой несимметричной нагрузке в замкнутом цикле;
бэкенд 50 мс по-прежнему определяет высокие перцентили.

*Сценарий ограничения частоты намеренно вернул 1150 ответов HTTP 429 и допустил
349 ответов HTTP 200. Это ожидаемый бюджет запаса и пополнения; поле «ошибки»
учитывает все статусы >=400. Отказ в допуске не является транспортной ошибкой.
30-секундный сценарий Compose k6 завершил 15001 запросов со скоростью 499.7/с:
3049 успешных и 11952 ожидаемых 429 (79.67%). Все проверки ответов пройдены.
Исходный вывод: [k6-rate-results.txt](k6-rate-results.txt).

Эксперимент с нестабильностью сочетает один сервер с независимой вероятностью
ошибки 25% и один здоровый сервер. Повторы повысили итоговую успешность с 87.413%
до 100% в этой выборке, увеличили число попыток на завершённый запрос примерно
с 1.00 до 1.124, повысили p95 с 4.295 мс до 4.802 мс и потребовали больше CPU.
Исключение по здоровью фактически отключено, чтобы отдельно изучить повторы.
Случайные значения отличаются между запусками.

## Полный стенд Compose

С тремя отдельными бэкендами 10 мс/50 мс/10 мс, JSON-журналами в stdout,
метриками, выборкой 10% трасс с учётом родительского решения и OTLP/Jaeger
k6 работал с 20 виртуальными пользователями 10 с. Завершено 8017 запросов
со скоростью 797.8/с, p50 11.78 мс, p95 51.95 мс, доля ошибок HTTP — 0%.
Оба настроенных порога пройдены.
[k6-throughput-results.txt](k6-throughput-results.txt).

Намеренный сценарий нестабильности всех бэкендов завершил 245294 запроса за 10 с.
Все проверки принимали заданные исходы 200/503, но 99.76% ответов были ошибками HTTP
после исключения трёх серверов. Это поведение быстрого отказа при аварии,
а не пропускная способность успешного проксирования. Только 578 запросов вернули 200.
Активные проверки восстановили готовность после прекращения нагрузки.
[Вывод сценария отказов](k6-failure-results.txt).

Материалы измерений записаны во время реализации. Последующее исправление
разделяет серии активных и пассивных ошибок здоровья: обычный успешный запрос
сбрасывает только пассивную серию. Повторите команды выше, чтобы измерить текущую
версию на своём оборудовании; таблицы сохраняют реальные ранее записанные выборки.

Исходный вывод: [benchmark-results.txt](benchmark-results.txt).
Микротест прокси включает создание тестового запроса и средства записи ответа,
сетевой ввод-вывод и работу бэкенда; это не чистые накладные расходы шлюза.
Микротесты балансировщика используют два сервера. Список префиксов выигрывает
при некоторых распределениях совпадений в начале; единственный эксперимент
с совпадением в середине не доказывает универсального преимущества дерева.

До замены срезов в пуле буферов на указатели на массивы и устранения обёрток
для пустых тел микротест прокси дал 263612 нс/операцию, 18884 байт/операцию,
168 выделений/операцию. [Вывод до изменения](benchmark-before-buffer-pool.txt).
Итоговая выборка приведена выше. Два изменения и неизолированные запуски не позволяют
приписать разницу времени одной оптимизации. Практически значимо уменьшение
числа выделений; повторите более длительные запуски с benchstat, прежде чем
заявлять устойчивое улучшение задержки.

## Профили и удерживаемая память

В 2-секундном CPU-профиле микротеста прокси 26.78% собственного времени пришлось
на обработку системных вызовов Linux, 25.42% — на ожидания futex среды выполнения.
Смешанный микротест клиента и бэкенда указывает на преобладание сокетного
ввода-вывода и планирования в короткой выборке; он не выявляет узкое место
исключительно шлюза. [Сводка CPU](cpu-profile-top.txt).

Выборочный профиль `alloc_space` отнёс 21.14% к созданию читателей bufio,
6.02% — к Request.WithContext, 5.35% — к Header.Clone. Это накопленные выделенные
байты, а не удерживаемая куча или свидетельство утечки.
[Сводка кучи](heap-profile-top.txt). Копии профилей представлены текстовыми сводками;
двоичные профили создаются заново командой `make profile`.

Владение горутинами проверяется исполняемыми тестами: завершение работы ожидает
допущенный запрос; отмена медленной проверки здоровья завершает рабочие циклы,
а `goleak` проверяет новые утечки горутин. Тесты потоковой передачи и отмены
проверяют освобождение счётчиков. Снимки выполняющихся запросов могут удерживать
старые маршруты до их срока; карты клиентских корзин ограничены и очищаются по TTL.
Для исследования удерживаемой памяти сравнивайте текущие `inuse_space`
и профили горутин после повторяющихся циклов нагрузки и перезагрузки.
Один `alloc_space` не доказывает стабильность объёма живой памяти.
